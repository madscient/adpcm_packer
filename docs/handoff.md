# adpcm_packer 開発引継ぎドキュメント

このドキュメントは、Claude (claude.ai chat) 上で行った `adpcm_packer` の
初期開発セッションの記録と、Claude Code に引き継ぐ際の申し送り事項をまとめた
ものです。コーディング規約・ビルド方法などの日常的な情報は `CLAUDE.md` を
参照してください。ここでは「なぜそうしたか」という経緯を中心に記載します。

## プロジェクトの背景

- ユーザーはレトロゲーム機の音源チップ（YM2608 / YM2610）向けサウンド
  ツールを開発している。
- 既存の `codec.h` / `codec.cpp`（Windows/MFC 環境で書かれた ADPCM
  エンコーダ実装）をユーザーから提供され、これをベースに CLI ツール
  `adpcm_packer` を新規構築した。
- 並行して `FITOM_X` という別プロジェクト（本セッションでは扱っていない）
  があり、そちら側のボイスパッチスキーマ再設計に合わせて `root_note`
  フィールドの要求仕様書が提示され、対応した。

## セッションの時系列と意思決定

### 1. codec.h/codec.cpp の移植・モダナイズ

元コードは Windows型 (`BYTE`, `DWORD`, `windows.h`) に依存していた。
`<cstdint>` ベースの型定義に置き換え、`ZeroMemory` 等の Windows API 呼び出し
を標準C++に置換した。**エンコードアルゴリズム自体（差分計算・ステップサイズ
テーブル等）はビット単位で変更していない** — 実機生成データとの互換性を
壊さないための方針。

`waveToAdpcm()` の WAV パースに、fmt チャンクの直後に data チャンクが
来ない WAV（拡張フォーマット等）にも対応できるよう、data チャンク探索
ループを追加した（元コードは fmt 直後決め打ちだった）。

### 2. CLI 化とパラメータJSON設計

- 単一の params.json で codec種別・出力レート・バウンダリ・複数WAVの
  入出力を指定する設計にした。
- 当初は自前の最小JSONパーサを実装したが、後に **nlohmann/json への
  置き換え**をユーザーから指示され対応。理由は明示されていないが、
  保守性・信頼性を優先する判断と思われる。自前パーサは完全に削除済み。

### 3. マルチプラットフォームビルド対応

- CMakeLists.txt を作成し、MSVC / GCC / Clang の3系統に対応。
- MSVC ビルドで実際に **C2220 (警告をエラー扱い) が発生**した
  （`std::transform` + `::tolower` の int→char 縮小変換、C4244警告）。
  ラムダで `static_cast<char>` するよう修正済み。**同様のパターンを
  今後追加する際は要注意**（`CLAUDE.md` に注記済み）。
- `/utf-8` はMSVC向けに必須（日本語コメント・メッセージのため）。

### 4. root_note 機能の追加（3段階で拡張）

ユーザーから提示された `adpcm_packer_root_note_requirements.md`
（FITOM_X側のスキーマ再設計に伴う要求仕様書）に基づき、以下の順で機能を
拡張した:

1. **固定値指定**: `root_note: 69`（整数, 0-127）。省略時デフォルト69。
   出力JSONには常に `root_note` を含める（省略しない）仕様。
2. **自動推定**: `root_note: "auto"` で YIN アルゴリズムによる基本周波数
   推定を追加。信頼度閾値未満はデフォルト69にフォールバック。
   `octave` フィールドで推定結果をオクターブ正規化する機能も同時追加。
   - 実装前に「修正規模とOSS活用について相談したい」という依頼があり、
     aubio / libfvad / WORLD vocoder 等の既存OSSを比較検討した上で、
     **依存ゼロの自前YIN実装**を選んだ（ビルド環境整備コストが機能規模
     に対して重すぎると判断）。この判断が妥当か、より高精度なピッチ
     推定が必要になった場合は再検討の余地がある。
3. **ノート名文字列対応**: `root_note: "A4"` のような表記も受け付ける
   よう拡張。`#`/`b` による変音記号、`C-1`〜`G9` の範囲に対応。

### 5. ディレクトリ構成の整理

当初フラットだった構成を `src/` / `test/` / `test/wav/` / `extern/` に
再編。CMakeLists.txt・README.md・.gitignore も追従済み。

### 6. ドキュメント・テスト整備

- README.md はユーザー向け仕様書として全パラメータを網羅する形で維持。
  機能追加のたびに更新している。**今後も機能変更時はREADME更新をセット
  で行うこと**。
- `test/` 以下に11本のテストJSON + 7本のテスト用WAVを整備。パラメータの
  全組み合わせ（整数/ノート名/auto/none、octave の有無、sample_rate の
  4パターン、boundary の2パターン等）を網羅している。

## Claude Code側での追加セッション

### ルートノート自動検出・ループポイント機能の追加

`pitch_estimator.h`/`loop_detector.h` を追加し、`root_note: "auto"` の
実装（本ドキュメント作成時点では未実装だった）と、`loop` フィールド
（`smpl` チャンク優先 → YIN周期ベース自動検出フォールバック）を実装した。
`wav_reader.h` を新設し、`codec.cpp` 側のWAVパースとは意図的に分離した
（`codec.cpp` はエンコード用リサンプリング込み、`wav_reader.h` はピッチ
推定・ループ検出専用の単純なPCM取り出しのみ）。詳細は `CLAUDE.md` の
アーキテクチャ節を参照。

### YMZ280B / OPL4-AWM (YMF278B) 対応の追加

既存の YM2608/YM2610 (ADPCM-A/B) に加え、YMZ280B（4bit ADPCM / 8bit・
16bit リニアPCM 選択式）と OPL4-AWM = YMF278B（8bit / 12bit / 16bit
リニアPCM、ADPCM非対応）への出力サポートを追加した。

- **一次情報の裏取り**: 自前の実装可能性を過信せず、`superctr/adpcm`
  リポジトリの `ymz_codec.c`（YMZ280Bのエンコードアルゴリズム）と、
  MAMEが現在採用している `aaronsgiles/ymfm` の `ymfm_pcm.cpp`
  （OPL4のPCMフォーマットのデコード側実装）、および両チップのデータ
  シート（`ymf278Bapplicationmanual.pdf` の EXTERNAL MEMORY DATA
  FORMAT節）を直接参照し、ニブル順・エンディアン・パック形式を
  相互検証してから実装した。特に **YMZ280Bの16bit PCMはリトル
  エンディアン、OPL4は逆のビッグエンディアン**という違いがあり、
  見落としやすいので注意。
- **設計判断（ユーザー確認済み）**: フォーマット選択は数値(1/2/3)では
  なく `"format": "adpcm"|"pcm8"|"pcm16"` 等の説明的な文字列にした。
  また、YMZ280B/OPL4は実チップ側でチャンネルごとに独立した再生レートを
  持てるため、`wav_files` の各エントリで `sample_rate` の個別上書きを
  許可した（ADPCM-A/B は既存どおりグローバル1本のまま変更していない）。
- **アーキテクチャ変更**: `AdpcmEncoder` 基底クラスに
  `samplesToBytes`/`bytesToSamples` の public 仮想関数を追加し、
  フォーマットごとに異なる bytes-per-sample 比率（ADPCM/YMZ280Bは
  2サンプル/1バイト、PCM8は1サンプル/1バイト、PCM16は1サンプル/2バイト、
  OPL4 PCM12は2サンプル/3バイト）を吸収できるようにした。以前は
  `waveToAdpcm()` が `dPcmSize/2` を決め打ちしており、これがYMZ280B/OPL4
  対応のボトルネックだった。`main.cpp` 側のループ点⇔バイトオフセット
  変換もこの仮想関数経由に一般化済み。
- **意図的なスコープ外**: このツールはチップのレジスタ値（YMZ280Bの
  FN/OCTAVE、OPL4のF-NUMBER/OCTAVE/wave table headerの12バイト構造等）
  を計算・出力しない方針を踏襲した。既存のADPCM-A/Bが `offset_hex`/
  `end_hex`/`root_note` を出すだけでレジスタ計算をダウンストリームの
  ドライバに委ねているのと同じ設計思想。YMZ280Bのsample_rateも、実際の
  FN量子化（クロック依存）はモデル化せず、任意のHzを指定してその通りに
  リサンプリングするだけに留めている（ドライバ側でFN値を逆算する前提）。
- 動作確認: 新規7テストJSON + 既存13テストJSON、計20本すべてで
  `完了。` を確認済み（MSVC `/W4 /WX` でも警告ゼロ）。

### YMZ705 (SSGS) / YMZ732 (SSGS2) 対応の追加

`codec: "ssgs"` を追加した。ユーザー指示により **YMZ705 と YMZ732 で
シンボルは共通の `"ssgs"`**、コーデックは YMZ280B の 4bit ADPCM と同一
（`Ymz280AdpcmEncoder` をそのまま流用）。

- **一次情報**: `YMZ705.pdf` / `YMZ732.pdf`（いずれもカタログ版データシート、
  スキャンPDFのためテキスト抽出不可。ページ画像として読解した）。
  ROMアドレスマップ・ADPCMコントロールレジスタマップを直接参照した。
- **設計判断（ユーザー確認済み）**:
  1. 出力バイナリは**アドレステーブルを含むROMイメージ全体**とする
     （ボイスデータのみの出力ではない）。
  2. ROMテーブル／JSONに書くエンドアドレスは**実データ末尾（包含）**。
     バウンダリ整列のパディングを再生範囲に含めない。既存の `end_hex`
     （パディング込み末尾）とは意図的に別フィールドにしている。
  3. **YMZ705 と YMZ732 を区別しない**。両者の差はシンプルアクセスコード用
     テーブル（YMZ732 の `$000240`〜`$00047F`）の有無だけで、この機能に
     対応しない前提であればROMマップは同一になるため。したがってボイス
     データ領域は両チップ共通で `$000240` から始まる。**将来シンプル
     アクセスモードに対応する場合はここが分岐点**になる（YMZ732 では
     データ領域が `$000480` から）。
  4. S1/S0 ビットとサンプリング周波数の対応（`00:4k / 01:8k / 10:16k /
     11:32k`）はカタログ版データシートに記載がなく、**ユーザーから提示された
     値**。出力JSONの `sampling_code` はこれに基づく。
- **既存コードへの影響**: `codecSupportsPerEntryRate()` が「per-entry
  sample_rate 上書きの可否」と「出力JSONに `format` を出すか」の2役を
  兼ねていたが、`ssgs` は前者だけ該当するため `codecHasFormat()` を分離した。
  また、ヘッダ領域のぶん先頭オフセットが boundary の倍数とは限らなくなった
  ため、各エントリのオフセットを `alignUp(currentOffset, boundary)` で
  都度求める形に変更した（既存 codec では従来と同じ結果になる）。
- 動作確認: 新規2テストJSON + 既存19テストJSON、計21本で `完了。` を確認。
  MSVC `/W4 /WX` で警告ゼロ。ROMテーブルのバイト列と出力JSONの
  `start_address`/`end_address` の一致、未使用スロット・曲テーブルの0埋め、
  boundary=256 時の先頭ボイス整列（`$000240` → `$000300`）を検証済み。
  入力/出力JSONは全21本を JSON Schema でも検証した。

### ADPCM-A/B のサンプル配置境界と memory_size の追加

それまでの配置は `alignUp(currentOffset, boundary)` だけで、サンプルがメモリの
境界をまたぐかどうかは見ていなかった。`adpcm-b` で 32KB 境界、`adpcm-a` で
1MB 境界をまたがない配置と、全 codec 共通の `memory_size` パラメータを追加した。

- **根拠となる資料**:
  - YM2608 (ADPCM-B): ユーザーが提示したアプリケーションマニュアルの
    スタート/ストップアドレスの項。アドレスは BANK(3bit)+CAS(9bit)+RAS(9bit)
    で、×1bit DRAM 構成の BANK は 8 個の DRAM のチップセレクト。
    「ROM / DRAM×8bit のときは BANK を start/stop で同じ値にする」とは
    書かれているが、×1bit 構成でチップ (32KB) をまたげるかどうかは、この
    ページには書かれていない。**32KB をまたがないのはユーザーの解釈で、この
    ツールの動作としては常にまたがない** (ユーザー判断。×1 構成の実際の
    挙動は調べる必要が無いとの指示で、資料調査は途中で打ち切った)。
    Y8950/YM2608 の ADPCM メモリは 256Kbit×1bit DRAM 1〜8 個 (上限 256KB)
    という構成はユーザーから提示された情報。
  - YM2610 (ADPCM-A): ユーザー提供の YM2610 アプリケーションマニュアル。
    「外部ROMにより最大連続1Mバイト／バンク切り替えで16Mバイト」「$18〜1D の
    D4〜D7 と $28〜$2D の D4〜D7 は同じでなくてはいけません」。
  - 同じマニュアルで、YM2610 の ADPCM-B は「最大連続16Mバイトまで可能」。
- **設計判断 (ユーザー確認済み)**:
  1. 境界をまたぐエントリは次の境界の先頭へ移動する (隙間は 0 埋め、
     `wav_files` の順序は変えない)。
  2. チップや構成で境界を切り替えない。`adpcm-b` は YM2610 向けでも常に
     32KB 規則で配置する。
  3. 境界サイズを超えるサンプルはエラーにする。
  4. メモリ容量は `memory_size` (バイト数、全 codec、省略時は検査なし) で
     指定し、超えたらエラー。出力JSONには出さない。
- **前提**: 32KB 規則が必要十分なのは YM2608 の ×1bit DRAM 構成のとき。
  ×8 / ROM 構成 (BANK 単位 256KB) と YM2610 の ADPCM-B (連続16MB) では
  規則が厳しすぎる。その結果、余白が増えるほか、32KB を超える ADPCM-B
  サンプルが作れない。この前提が崩れた (YM2610 で 32KB 超の ADPCM-B が
  必要になった) 場合は、チップか境界サイズを指定するパラメータを追加する。
  その場合の変更箇所は `sampleBankFor()`・`loadParams()`・入力スキーマ・
  README・テストJSON。
- **見送った案**:
  - 境界をまたいだらエラーにするだけの案。見送った理由: 利用者が並び順を
    手で調整する必要が出るため。
  - 隙間を後続の短いサンプルで埋める詰め直し案。見送った理由: 出力の並びと
    アドレス順がずれ、設計の変更が大きいため。
  - 境界サイズをパラメータ化する案。見送った理由: ユーザー判断で「常に避ける」。
  - 32KB を超えるサンプルを警告だけで通す案。見送った理由: ユーザー判断で
    エラー。
  - `adpcm-b` で合計 256KB を超えたら警告する案。`memory_size` に置き換えた。
  - `memory_size` を出力JSONにも出す案。見送った理由: 下流のドライバが使う
    情報ではないため (後からの追加は可能)。
- **動作確認 (確認済み)**:
  - 新規3テストJSON + 既存21本の計24本で `完了。` を確認し、MSVC `/W4 /WX`
    で警告ゼロ。入力24本・出力24本を JSON Schema で検証した。
  - `test_adpcm_b_chip_boundary.json` と `test_adpcm_a_1mb_boundary.json` は、
    変更前のビルドでは各1エントリが境界をまたぐ配置になり、変更後はまたがない
    ことを確認した。移動したエントリのデータが変更前と同一であることと、
    隙間が 0 埋めであることは ADPCM-B のテストで確認した。
  - `memory_size` は、ちょうど収まる値で成功し、1 小さい値でエラーになる。
    不正値 (0, -1, 文字列, 小数, 2^32) は実行時・スキーマの両方で弾かれる。
  - 32KB を超える ADPCM-B サンプル (3秒の WAV を 32kHz で符号化) はエラーに
    なる。ループ点を持つエントリを移動させたとき、ループ点のバイト
    オフセットが移動先に追従する。これらは一時ファイルで確認しただけで、
    テストJSONには含めていない。
  - 既存テストのうち `test_loop.json` の `loop_none` は 32KB をまたいでいたため、
    `0x7000` から `0x8000` へ移動する (`total_size` も 36864→40960)。
- **boundary の案内の修正**: README の boundary 表は「ADPCM-A は 32 byte 境界、
  ADPCM-B (YM2608/YM2610) は 256 byte 境界」としていたが、YM2610 の
  マニュアルでは ADPCM-A・ADPCM-B ともアドレス分解能は 256 バイトで、
  YM2608 の最小単位は ×8 構成で 32 バイト、×1 構成で 4 バイト。表を
  「32: YM2608 の ADPCM-B / 256: YM2610 の ADPCM-A・ADPCM-B」に直し、
  `test_basic_adpcm_a.json` を `boundary: 256` に変更した (ユーザー判断:
  ADPCM-A は通常 256 バイト単位でしか使われない)。`adpcm-a` + `boundary: 32`
  をツール側で弾く・警告する処理は入れていない。

### ADPCM エンコーダの 32bit 桁あふれ (修正済み)

ADPCM-B で `test_noise.wav` の符号化結果が実行ごとに変わる現象を調べた。
以下はすべて確認済み (scratch での実行・Python による再現)。

- **原因 (修正前のコード)**: `YmDeltaTEncoder::encode()` の
  `long i = (std::abs(dn) << 16) / (stepSize << 14);` は、Windows (LLP64) では
  `long` が 32bit のため、|dn| ≥ 32768 で桁あふれして `i` が負になる。
  `if (i > 7)` の上限処理をすり抜けて `adpcm` が 16 以上の値 (例: 252) になり、
  16 要素の `stepsizeTable[adpcm]` を範囲外で読む。範囲外の値は実行ファイルの
  ロード位置 (ASLR) で変わるため、結果が実行ファイルごとに変わる。
- **証拠**:
  - 32bit の挙動を再現した Python モデルでは、`test_noise.wav` (16kHz) の
    28 サンプル目で `adpcm = 252`。実際の出力の 15 バイト目は `0xC0`
    (64bit の経路なら上位 nibble は `F`) で、32bit の経路を通っている。
  - 中身が同じ実行ファイルを別名で5つ複製すると 4 通りの出力になり、各複製は
    繰り返し実行しても安定。PE ヘッダの DYNAMIC_BASE を落とした複製5つは
    すべて一致。
  - 166 行目を 64bit で計算するよう一時的に書き換えたビルドでは、ASLR 有効の
    複製5つが一致し、出力は 64bit の Python モデルと 4000 バイト全部一致した
    (確認後、codec.cpp は元に戻した)。
  - 64bit で計算した場合に |dn| ≥ 32768 となるのは `test_noise.wav` で 314 回。
    サイン波のテスト音では起きない。
- **同じ形の式**: `Ymz280AdpcmEncoder::encode()` (YMZ280B / SSGS 共用) の
  `(std::abs(diffIn) << 16) / (stepSize << 14)` も同じく桁あふれする。表の添字は
  `adpcm & 0x7` なので範囲外読みは起きず、結果は揺れない。それでも 16 以上の値が
  隣の nibble に OR されるため、データは化ける。`test_ssgs.json` の
  `test_noise.wav` エントリは 32bit モデルと完全一致し、64bit モデルとは
  4000 バイト中 2024 バイトが違う。ADPCM-A エンコーダは `int` で 12bit 値を
  扱っており、この形の式は無い。
- **プラットフォーム差 (推測)**: `long` が 64bit の LP64 環境 (Linux/macOS の
  GCC/Clang) では修正前からこの桁あふれは起きず、64bit モデルと同じ出力だった
  はず。修正後は Windows でも 64bit モデルと一致するので、差は無くなったはず。
  Linux ビルドで実行してはいない。
- **修正 (ユーザー承認済み)**: 2 式を `int64_t` で計算するよう変更した。
  `|d|*4/step` と同値だが、参照実装と同じ形の式を残すため 64bit 化を選んだ。
  CLAUDE.md の「エンコードアルゴリズムのロジックを変更しない」の例外として
  CLAUDE.md にも記載した。
- **修正の確認 (確認済み)**:
  - 全24テストで `完了。`。修正前の出力と比べて変わったのは
    `test_rootnote_auto` の `auto_noise_fallback`・`test_loop` の
    `loop_detect_fallback`・`test_ssgs` の `test_noise` の3エントリのデータだけで、
    出力JSONは全テストで同一、エントリ外 (SSGS のテーブル領域・パディング) の
    差分も無い。
  - 3エントリとも、修正後の出力は 64bit の Python モデルと全バイト一致する
    (修正前は ADPCM-B が範囲外読みで不定、SSGS は 2024 バイト不一致)。
  - ASLR 有効の複製5つで、`test_rootnote_auto`・`test_loop` の出力はそれぞれ
    1 通りになる (修正前は 5 つで 4 通り)。

### ADPCM-B エンコーダの予測値クランプ (修正済み)

`YmDeltaTEncoder::encode()` は予測値 `xn` をクランプしていなかった。振幅 ±32766 の
サイン波でも 16kHz・8000 サンプル中 236 回、`xn` が ±32767 を超えていた
(最大 33424)。

- **デコーダ側の扱い (確認済み。ソースを取得して該当行を確認)**: ymfm
  (`adpcm_b_channel::clock()` の `clamp(m_accumulator + delta, -32768, 32767)`)、
  旧 MAME `ymdeltat.cpp` (`YM_DELTAT_Limit(DELTAT->acc, ...)`)、
  superctr/adpcm `ymb_codec.c`、ngdevkit `adpcmtool.py` は、いずれも累算値を
  1 ステップごとに [-32768, 32767] へ飽和させる。superctr と ngdevkit の
  エンコーダは、クランプ後の値を自分の予測値として持つ。ステップ幅の範囲
  [127, 24576] は全実装と YM2608 マニュアル (英訳版) で一致。
- **前提**: 実チップも累算値を 16bit に飽和させること。これは未確認で、根拠は
  エミュレータと他のエンコーダの実装だけ (YM2608 マニュアルの英訳版には xn の
  上下限の記述が無い)。実チップが飽和させないと分かった場合は、codec.cpp の
  クランプ 2 行を外す。
- **クランプ前の影響 (確認済み。Python モデルで ymfm と同じ更新式のデコーダを
  通した)**: エンコーダが追う波形とデコード結果が、フルスケールのテスト音で
  最大 657〜1224 ずれ、入力に対する SNR が 0.2〜0.6 dB 下がっていた。
  振幅 ±12000 の音では差が無い。
- **修正 (ユーザー承認済み)**: `xn` の更新直後に [-32768, 32767] へクランプする。
- **修正の確認 (確認済み)**:
  - 全24テストで `完了。`、MSVC `/W4 /WX` で警告ゼロ。
  - ADPCM-B の全 49 エントリで、実際の出力がクランプありの Python モデルと
    全バイト一致する (クランプ前の出力で一致するのは 49 中 4 エントリ。この 4 は
    振幅が小さく、予測値が範囲を出ないもの)。
  - 49 エントリとも、実際の出力を ymfm と同じ更新式でデコードした結果が、
    エンコーダの予測値の列と完全に一致する。
  - 出力バイナリが変わったのは ADPCM-B のテスト 12 本すべて。出力JSONは全テストで
    同一で、ADPCM-B 以外のテストのバイナリは変わっていない。
- **参考**: superctr の量子化式は 32bit `int` で計算しており、本ツールの
  桁あふれ修正前と同じ桁あふれを持つ (scratch で gcc を使って確認)。

## 未対応・今後の検討事項

- **実チップの ADPCM-B デコーダが累算値を飽和させるかの確認**: 上の
  「予測値クランプ」節の前提。実機での録音比較か、YM2608 マニュアルの
  日本語原文で確かめる。

- **fine_tune_cents**: root_note要求仕様書内で「将来的な拡張候補」として
  言及されている、セント単位の微調整値。半音単位の `root_note` では
  表現できない厳密なピッチのズレを扱う場合に必要になる。現時点ではスコープ
  外として未実装。
- **自動テストの仕組み化**: 現状は `test/*.json` を手動実行して目視確認
  するのみ。CI連携や、出力JSONの期待値との自動比較（回帰テスト）は
  未整備。テストWAVがサイン波の合成音のみのため、実機録音サンプルでの
  検証もされていない。
- **YINの精度**: 単音のサイン波・楽器音では良好に動作することを確認して
  いるが、和音・打楽器・SE系サンプルでの挙動は未検証。信頼度フォールバック
  で安全側に倒す設計にはなっているが、閾値0.75の妥当性はチューニングの
  余地がある。
- **FITOM_X側との実際の疎通確認**: 出力JSONのフィールド名・値の意味が
  FITOM_X側の期待と一致しているかは、要求仕様書の記述をベースに実装した
  のみで、FITOM_X側との実データでの突き合わせは行っていない。
- **Clang / macOS でのビルド確認**: 未実施。CMakeLists.txt上は対応して
  いる想定だが実機検証はしていない。
- **SSGS のシンプルアクセスモード**: YMZ732 のシンプルアクセスコード
  (No.64〜255) 用テーブルは未対応。対応する場合は YMZ705 と YMZ732 の
  ROMレイアウトを分ける必要がある（`main.cpp` の `ssgs::DATA_AREA_BASE`
  が分岐点）。
- **SSGS の曲データ**: 曲データ（シーケンサ用データ）の生成には対応して
  いない。ROMイメージ内の曲データ用テーブル (`$000180`〜`$00023F`) は
  0埋めのまま出力される。
